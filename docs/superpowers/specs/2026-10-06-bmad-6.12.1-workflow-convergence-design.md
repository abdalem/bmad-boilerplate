# BMAD 6.12.1 Boilerplate Workflow Convergence

**Status:** Approved for implementation by the 2026-10-06 completion request
**Date:** 2026-10-06
**Target repository:** `abdalem/bmad-boilerplate`
**Target BMAD version:** `6.12.1`

## Context

The boilerplate already implements an adaptive BMAD Work Item model built around:

- `Module`
- `Request`
- `Feature`
- `Issue`
- `Bug`
- `Spike`

It correctly treats the configured project-management system as authoritative for identity, hierarchy, status, assignment, and priority.

It also already provides:

- `bmad-start-project`
- `bmad-update-project`
- `bmad-workflow-setup`
- `bmad-publish-work-item`
- `bmad-close-work-item`
- ticket-scoped planning and implementation artifacts
- `bmad-build` customization
- Figma routing
- no-automatic-commit policy
- managed workflow-pack installation and migration
- Codex and Claude Code support

The current workflow was designed around BMAD 6.11.

BMAD 6.12 fundamentally changes Build:

> Build now investigates first and decides how much ceremony is required afterward.

A small change may remain a two-section implementation spec and complete in one session. More complex changes automatically receive the deeper planning path.

BMAD 6.12 also embeds independent review directly into Build through:

- Blind Hunter
- Edge Case Hunter
- Verification Gap Reviewer

BMAD 6.12.1 additionally makes all BMM skills consume the same merged configuration, so `_bmad/custom/config.toml` and user overrides behave consistently across the framework.

The boilerplate should therefore converge toward upstream BMAD rather than continue maintaining custom equivalents of behavior now provided natively.

---

# Goals

1. Make BMAD 6.12.1 the tested and reproducible baseline.

2. Preserve one consistent workflow across:
   - new projects,
   - adopted existing repositories,
   - small changes,
   - large features,
   - bugs,
   - research work.

3. Preserve the current semantic Work Item model:

   `Module -> Feature -> Issue`

   plus:

   `Request`, `Bug`, and `Spike`.

4. Keep external project-management tools authoritative.

5. Make `bmad-build` the default implementation engine.

6. Exploit BMAD 6.12's adaptive planning instead of duplicating complexity routing outside Build.

7. Reduce repeated context loading and custom workflow instructions.

8. Remove obsolete pre-6.12 compatibility behavior from the managed workflow pack.

9. Preserve the current KISS and no-auto-commit engineering policy.

10. Keep the boilerplate usable with multiple trackers and both Codex and Claude Code.

---

# Non-Goals

This migration must NOT:

- introduce Stories as the normal delivery unit;
- introduce Epics as a parallel tracker hierarchy;
- introduce sprint planning or sprint-status artifacts;
- reproduce tracker state inside BMAD;
- bring back S/M/L workflow classification;
- require a PRD for ordinary engineering work;
- require a SPEC for every Work Item;
- run every available BMAD skill on every ticket;
- require standalone code review after every Build;
- require a repository-wide scan before every change;
- automatically commit, push, or create a pull request;
- rewrite completed historical `_bmad-output` artifacts;
- replace project-specific tracker terminology with hardcoded ClickUp terminology.

---

# Core Principle

The new architecture must be:

```text
Tracker
    |
    | owns identity, hierarchy, status, priority, assignment
    v
Work Item / Intent
    |
    v
BMAD
    |
    | investigates and decides required ceremony
    v
Build
    |
    | implementation + verification + integrated review
    v
Close
```

BMAD is the **product refinement and engineering execution system**.

It is not the project-management system.

# 1. Pin BMAD 6.12.1

The boilerplate currently defaults to:

```text
bmad-method@latest
```

This is inappropriate for a reusable workflow baseline.

Two projects created from the same boilerplate version at different dates can currently receive different BMAD behavior.

Change the tested default to:

```text
bmad-method@6.12.1
```

Update all canonical definitions, generated/template equivalents, tests, and documentation.

This includes at minimum the places currently defining or asserting the installer version, such as:

- `.boilerplate/bmad-workflow-pack/pack.json`
- `scripts/install-bmad.sh`
- `templates/base/scripts/install-bmad.sh`
- boilerplate CLI/scaffold logic
- workflow-pack tests
- package scripts where relevant

The normal command:

```bash
pnpm bmad:install
```

must install the pinned tested release.

Provide separate explicit commands for evaluation.

Suggested semantics:

```text
bmad:install
    -> tested/pinned BMAD 6.12.1

bmad:install:stable
    -> same tested version

bmad:install:latest
    -> current upstream stable for compatibility testing

bmad:install:preview
    -> bmad-method@next
```

Do not silently move production projects to a new BMAD version when upstream publishes one.

A BMAD version bump should become an explicit boilerplate maintenance operation:

```text
evaluate upstream version
        ->
run workflow-pack compatibility suite
        ->
adapt managed overrides if required
        ->
update pinned version
        ->
release boilerplate
```

Consider bumping the workflow pack from `2.1.0` to a new major/minor version reflecting the 6.12 convergence.

# 2. Keep the semantic Work Item model

Retain the current six semantic roles:

| Type | Meaning |
| --- | --- |
| Module | Long-lived product/capability area |
| Request | Incoming demand requiring qualification |
| Feature | Cohesive user/business capability |
| Issue | Independently deliverable engineering change |
| Bug | Incorrect existing behavior |
| Spike | Time-boxed investigation producing evidence/decision |

Project-specific tracker names may map onto these roles through:

```text
_bmad/custom/project-workflow.toml
```

Do not introduce:

- Story
- Epic
- Task
- Improvement

as mandatory boilerplate concepts.

A tracker may itself use any terminology, but the boilerplate's semantic mapping must remain stable.

---

# 3. Change the normal daily entry point

The current documentation says normal established-project delivery begins with:

```text
bmad-publish-work-item
```

This was appropriate before BMAD 6.12.

It should no longer be mandatory for every actionable ticket.

## New rule

For an existing sufficiently actionable:

- Feature
- Issue
- Bug

the normal path is:

```text
Tracker Work Item
        |
        v
   bmad-build
        |
        v
bmad-close-work-item
```

Build receives:

- a tracker URL,
- tracker ID,
- local Work Item path,
- pasted requirement,
- or explicit user intent.

BMAD 6.12 then decides how much planning the change needs.

### Examples

```text
Implement LIM-726.
```

or:

```text
Implement this Work Item:
<url>
```

or:

```text
Use bmad-build for the following bug:
...
```

Do not require a separate `work-item.md` simply because BMAD historically needed one.

---

# 4. Reposition `bmad-publish-work-item`

Do NOT remove `bmad-publish-work-item`.

It remains useful, but its responsibility changes.

Use it when the user needs to:

- create a new tracker item;
- qualify a Request;
- refine a vague Work Item;
- establish product scope;
- determine observable acceptance criteria;
- define fixed product decisions;
- determine Feature vs Issue vs Bug vs Spike;
- decompose a non-cohesive Feature;
- synchronize a refined contract back to the tracker.

It is a **product refinement / publication skill**, not a mandatory engineering gateway.

The rule becomes:

```text
Already actionable?
    |
    +-- yes -> bmad-build
    |
    `-- no  -> bmad-publish-work-item
                   |
                   +-> Build
                   +-> Spec
                   +-> UX
                   +-> research
                   +-> architecture
                   `-> child Work Items
```

`bmad-publish-work-item` should not duplicate Build's implementation investigation.

Its evidence scan should stay at the altitude needed to define correct product behavior.

Do not investigate:

- exact files,
- functions,
- classes,
- local abstractions,
- implementation sequence,
- detailed test structure,

unless one of them exposes a product contradiction.

---

# 5. Allow Build with or without `work-item.md`

The current managed `bmad-build.toml` requires:

```text
_bmad-output/planning-artifacts/<id>/work-item.md
```

and routes back to publication when the file is absent.

Remove that hard requirement.

Build should support two modes.

## Tracker-native mode

Input:

```text
tracker Work Item / pasted intent
```

No local `work-item.md` is required.

BMAD Build performs its normal 6.12 investigation and creates whatever implementation spec it requires.

## Refined-contract mode

When `work-item.md` exists, Build reads it and treats these sections as binding:

- Scope
- Non-Goals
- Acceptance Criteria
- Fixed Decisions
- approved design references

Build must not repeat product discovery already captured there.

The rule is therefore:

```text
work-item.md exists
    -> inherit it

work-item.md absent
    -> use supplied intent / tracker context
```

Do not force generation of an artifact merely to satisfy workflow ceremony.

---

# 6. Let Build own implementation complexity

Remove any remaining custom logic that tries to determine implementation complexity before Build.

BMAD 6.12 Build already decides after investigation whether the work requires:

- a tiny implementation spec,
- deeper clarification,
- larger planning,
- implementation handoff,
- review and repair.

Do not recreate S/M/L under another name.

The external workflow only decides whether Build is the correct capability.

For example:

```text
Issue
  -> Build

Bug
  -> Build

cohesive Feature
  -> Build

unclear product behavior
  -> Publish/Spec first

cross-unit architectural invariant
  -> Architecture first

Spike
  -> Research

Request
  -> Qualification

Module
  -> child Feature/Issue
```

---

# 7. Preserve Work Item decomposition outside BMAD stories

When a Feature is too large to remain one independently verifiable delivery unit:

```text
Feature
  |
  +-> Issue
  +-> Issue
  `-> Issue
```

Create these children in the configured tracker.

Do NOT create BMAD Stories to substitute for them.

Do NOT maintain a second decomposition under:

```text
epics-and-stories/
stories/
sprint-status.yaml
```

Each child Issue can independently enter:

```text
bmad-build
```

BMAD may still ship story-related capabilities upstream.

The boilerplate simply does not route normal work through them.

---

# 8. Simplify `bmad-build.toml`

Audit the 6.12.1 upstream `bmad-build/customize.toml` before editing the override.

Use only supported fields.

The managed override should remain very small.

## Keep

### No automatic Git operations

Build must never automatically:

- commit;
- push;
- create a PR.

Explicit user approval remains mandatory.

### Project governance

Implementation subagents must read the repository `AGENTS.md`.

### Refined contracts

When a ticket-scoped Work Item contract exists, Build inherits its binding product constraints.

### KISS

Prefer the smallest clear implementation satisfying the requirement.

---

## Remove

Do not persistently load:

```text
docs/bmad-work-item-workflow/index.md
```

during every Build.

BMAD 6.12 intentionally ships Build with empty `persistent_facts`.

The workflow documentation is reference material, not implementation context.

Do not pay its token cost on every Work Item.

Also remove duplicated generic explanations that Build itself already knows.

Prefer:

```text
AGENTS.md
+
current Work Item / spec
+
targeted code
```

over large persistent context.

---

# 9. Preserve upstream Build review layers

Do not replace or duplicate the default BMAD 6.12.1 review pipeline without a proven project-specific reason.

Retain upstream:

```text
Blind Hunter
Edge Case Hunter
Verification Gap Reviewer
```

The boilerplate should inherit upstream review layers rather than copying their definitions into its own TOML.

This lets future BMAD compatibility upgrades improve the review implementation without requiring duplicate boilerplate maintenance.

Project overrides should change review layers only when a project has a concrete reason.

---

# 10. Remove mandatory post-Build code review

The current workflow help still implies:

```text
bmad-build
    ->
bmad-code-review
    ->
close
```

as a common route.

BMAD 6.12 Build already includes independent review and repair.

The default path should therefore become:

```text
bmad-build
    ->
bmad-close-work-item
```

Use standalone `bmad-code-review` when:

- code was written outside BMAD Build;
- reviewing another developer's branch or PR;
- the user explicitly requests an additional independent review;
- project risk calls for another specialist review;
- reviewing a historical/existing diff.

Do not automatically review reviewed code again.

---

# 11. Reassess `bmad-review-verification-gap`

The boilerplate currently ships an internal:

```text
bmad-review-verification-gap
```

BMAD 6.12 Build now includes an upstream Verification Gap Reviewer.

Audit whether the custom skill still provides any unique value.

If its only normal use is:

```text
Build -> verification gap review
```

retire it from the normal managed workflow.

Remove it entirely if no independent standalone use case remains.

If retained, clearly redefine it as something such as:

> Standalone verification audit for code that did not go through BMAD Build.

It must not be automatically executed after every Build.

---

# 12. Replace deprecated Checkpoint terminology

BMAD 6.12 renamed:

```text
bmad-checkpoint-preview
```

to:

```text
bmad-walkthrough
```

Update managed documentation, help overlays, tests, aliases, and generated references to use:

```text
bmad-walkthrough
```

as the canonical identifier.

Do not depend on deprecated compatibility shims.

Where practical, install BMAD without deprecated shims and make the boilerplate validation fail when managed assets reference one.

---

# 13. Use `bmad-project-context` as the AGENTS.md maintainer

BMAD 6.12 substantially improved `bmad-project-context`.

Use it as the standard mechanism to establish and maintain concise repository instructions.

For new projects:

```text
bmad-project-context setup
```

For adopted existing repositories:

```text
bmad-project-context adopt
```

Later:

```text
refresh
record
audit
```

The repository's `AGENTS.md` should contain only information agents cannot cheaply and safely rediscover.

Examples:

- no automatic commit/push/PR;
- repository-specific dangerous commands;
- important architectural constraints;
- unusual verification commands;
- project-specific domain pitfalls;
- security/governance constraints.

Do not duplicate information already obvious from:

- package manifests;
- build scripts;
- CI;
- source code;
- normal framework conventions.

When an agent repeatedly makes a mistake, prefer:

```text
bmad-project-context record
```

over adding more text to every skill customization.

# 14. Reduce custom TOML surface

Audit every file under:

```text
.boilerplate/bmad-workflow-pack/bmad-custom/
```

For each customization, classify it as:

```text
KEEP
SIMPLIFY
REMOVE
```

Remove overrides whose only job is to repeat:

- KISS;
- generic Work Item folder explanations;
- instructions already in `AGENTS.md`;
- upstream BMAD behavior;
- obsolete story/sprint behavior;
- redundant review routing.

Retain an override when it actually changes project behavior, for example:

- ticket-specific output location;
- Figma integration;
- external tracker behavior;
- no-auto-commit;
- project-specific artifact placement;
- Work Item contract inheritance;
- specialist output routing.

The target is **few meaningful overrides**, not blanket customization of every BMAD skill.

# 15. Reduce persistent context

Review every use of:

```toml
persistent_facts = [...]
```

Apply this rule:

> Persistent context must be required throughout the entire skill run and must materially affect decisions.

Do not load documentation simply because it is relevant to the broader methodology.

Prefer targeted reads triggered by the current Work Item.

Typical Build context should approach:

```text
AGENTS.md
current intent / tracker Work Item
optional work-item.md
Build spec
relevant source
relevant tests
```

not:

```text
whole workflow manual
project lifecycle docs
all planning artifacts
all architecture docs
all historic Work Items
```

# 18. Final daily workflow

The documentation should prominently show this table.

| Situation | Normal action |
| --- | --- |
| Existing actionable Issue | `bmad-build` |
| Existing actionable Bug | `bmad-build` |
| Existing cohesive Feature | `bmad-build` |
| New/unclear item | `bmad-publish-work-item` |
| Request | `bmad-publish-work-item` / qualification |
| Module | define child Feature/Issue |
| Spike | targeted research |
| Unclear acceptance/behavior | `bmad-spec` |
| UX/design change | `bmad-ux` + Figma |
| Cross-unit architecture risk | `bmad-architecture` |
| Human review walkthrough | `bmad-walkthrough` |
| Code not produced through Build | optional `bmad-code-review` |
| Completed delivery | `bmad-close-work-item` |

The desired common case is intentionally short:

```text
Work Item
   ->
Build
   ->
Close
```

---

# 19. Bug workflow

Do not create a separate lifecycle for Bugs.

A Bug remains a Work Item with defect-specific evidence.

Normal:

```text
Bug
 ->
Build
 ->
Close
```

Build should determine:

- reproduction;
- root cause;
- minimum safe fix;
- regression verification.

Critical Bugs additionally require:

- minimum safe restoration;
- production/rollout verification;
- rollback readiness;
- monitoring or detection status.

Priority changes safeguards, not methodology.

---

# 20. Spike workflow

A Spike is explicitly not normal production implementation.

Target:

```text
question
  ->
targeted investigation
  ->
evidence
  ->
decision
```

Then either:

```text
close Spike
```

or create:

```text
Feature
Issue
Bug
```

as follow-up Work Items.

Do not route a Spike through Build unless the user explicitly converts it into implementation work.

# 21. Artifact policy

Keep ticket-scoped artifacts, but only create files that add value.

Example:

```text
_bmad-output/
  planning-artifacts/
    app-001/
      work-item.md        # optional; exists when refinement/publication occurred
      spec/               # only when needed
      research/           # only when needed
      ux/                 # only when needed

  implementation-artifacts/
    app-001/
      ...                 # Build/review/test evidence only when useful
```

Do not create empty directories.

Do not create placeholder artifacts.

Do not maintain:

```text
stories/
epics-and-stories/
sprint-status.yaml
```

as part of the boilerplate workflow.

`_bmad-output` remains temporary working memory.

Durable knowledge belongs in maintained project documentation.

# 22. Closeout remains mandatory for managed Work Items

Keep `bmad-close-work-item`.

Its responsibilities remain valuable:

- verify acceptance;
- ensure fixed decisions were respected;
- verify bug resolution where applicable;
- update tracker state;
- transfer durable knowledge;
- update design registry/references when required;
- optionally update release notes;
- identify follow-up Work Items;
- prepare ticket-scoped cleanup;
- delete artifacts only after explicit approval.

It must not require:

- BMAD stories;
- sprint completion;
- duplicate review artifacts.

When Build already performed independent review, closeout should consume that evidence rather than launch another generic review.

# 33. Success Criteria

The migration is successful when:

1. BMAD 6.12.1 is the tested default.

2. A developer with a clear existing Issue normally runs:

   ```text
   bmad-build
   ```

   directly.

3. `bmad-publish-work-item` remains available for Work Item creation and genuine product refinement but is no longer mandatory before every Build.

4. A simple Issue can complete through:

   ```text
   Build -> Close
   ```

5. Build decides implementation ceremony adaptively.

6. Build inherits upstream independent review.

7. Standalone code review is optional rather than duplicated.

8. `bmad-review-verification-gap` is removed or clearly restricted to a standalone use case.

9. `bmad-walkthrough` replaces the deprecated checkpoint identifier.

10. The standard workflow contains no Story, Epic, sprint, S/M/L, or Quick Dev dependency.

11. Tracker hierarchy remains external.

12. Module, Request, and Spike cannot accidentally enter normal production Build routing.

13. `AGENTS.md` is maintained through `bmad-project-context`.
